# 리뷰 루프 — 언제 고치고 언제 방식을 바꾸나

PR 리뷰를 처리할 때 읽는다. `CLAUDE.md` 에 있던 절을 옮겼다(2026-09-29) — 매 세션 읽힐
필요는 없고 리뷰가 올 때 필요하다. **작업 지침으로 고정되어 있다**(`AGENTS.md`).

PR 리뷰(Codex 등)의 지적을 **라운드마다 점수로 센다.** 점수는 분류를 요약할 뿐이고,
분류는 **실행으로** 가른다 — 같은 입력을 `main` 과 이 PR 에 넣어 보고, 저장소의 실제
파일에서 재현해 본다.

| 지적의 분류 | 점수 | 가르는 법 |
|---|---|---|
| 실결함 | 10 | 저장소의 실제 파일이나 CI 에서 재현된다 |
| 회귀 | 5 | 같은 입력에서 `main` 은 맞고 이 PR 은 틀린다 |
| 기존 한계 · 조용한 통과 | 2 | 저장소에 그런 입력이 없고 `main` 도 똑같이 놓친다 |
| 기존 한계 · 시끄러운 실패 | 1 | 저장소에 그런 입력이 없고 `main` 도 똑같이 실패시킨다 |
| 반박됨 | 0 | 재현을 시도했으나 지적한 현상이 어디서도 나오지 않는다 — 답글에 그 시도를 남긴다 |

한 지적은 **위에서부터 먼저 맞는 분류 하나**로만 센다 — 저장소의 실제 입력에서 틀리면
`main` 과 견줄 것 없이 실결함이다. 라운드 점수(그 리뷰의 합)로 다음을 정한다.

- **5 이상** — 고치고 계속한다
- **1 ~ 4** — 고친다. **두 라운드 연속**이면 아래 방안을 검토한다
- **0** — 머지를 권한다. 머지는 저장소 소유자가 한다

**쏠림 신호.** 점수와 따로, 같은 **변경 단위**(함수 · 문서의 절 · 워크플로 스텝)를 짚은
지적이 두 라운드 연속 나오고, 두 라운드를 합쳐 그 단위의 지적이 세 건 이상이며 두
라운드 지적의 과반(절반 초과)이면 점수가 높아도 고치기를 멈추고 방안을 검토한다 — 고칠
때마다 새 틈이 나는 신호다. 라운드마다 한 건씩(합계 둘)이거나 단위마다 흩어져 있으면 이
신호가 아니다. ERP#18 은 2 라운드에 이 신호가 섰는데 3 라운드 뒤에야 방식을 바꿨다.

방안은 위에서부터 먼저 맞는 것을 쓴다.

| 방안 | 조건 | 소유자에게 묻는 것 |
|---|---|---|
| A. 진짜 구현으로 바꾼다 | 지적의 절반 이상이 한 규격을 손으로 흉내 낸 코드에 있고, 그 규격의 유지되는 구현이 있으며, 비용이 개발 의존성 하나 이하 · 운영 의존성 0 이다 | 의존성 추가 |
| B. 입력을 계약으로 좁힌다 | 검사 대상이 우리가 쓰는 몇 파일이고, 새 규칙에서 지금 걸리는 줄이 0 이거나 몇 줄이다 | 사람이 지킬 작성 규칙이 새로 생기면 |
| C. 기준 구현과 대조해 잰다 | 기준 구현이 있다. 무작위 입력 1만 개 이상에서 `main` 과 이 PR 의 판정을 **각각 기준 구현의 판정과 견준다** — `main` 이 맞고 이 PR 이 틀리면 「새로 틀림」, 반대면 「바로잡음」이다. **새로 틀림이 0.1% 미만**이고 바로잡음이 새로 틀림보다 많으면 받아들인다. 입력 생성기와 시드(또는 생성한 입력 묶음)를 PR 에 남겨 누구나 다시 돌릴 수 있게 한다 | 없음 — 결과를 보고한다 |
| D. 알려진 한계로 적는다 | 남은 것이 모두 기존 한계 · 시끄러운 실패다 | 없음 — `AGENTS.md` 에 적는다 |
| E. 후속으로 뗀다 | 지적이 이 PR 이 바꾼 변경 단위 밖이거나, 남은 것이 조용한 통과다 | 없음 — 조용한 통과는 D 로 덮지 않는다 |

신호가 섰는데 **어느 방안도 조건에 맞지 않거나**, 방안을 적용하고도 두 라운드 더 실결함 ·
회귀가 나오면 **혼자 더 고치지 않고** 분류표를 들고 소유자에게 묻는다(ERP#20 3 라운드가
앞의 경우였다). PR 을 보고할 때는 라운드 점수의 추이를 한 줄로 적는다(ERP#18 을 되짚어
매기면 `10 → 15 → 19 → 2 → 5 → 2 → 0`).
