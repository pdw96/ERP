# 리뷰 루프 — 언제 고치고 언제 방식을 바꾸나

PR 리뷰를 처리할 때 읽는다. `CLAUDE.md` 에 있던 절을 옮겼다(2026-09-29) — 매 세션 읽힐
필요는 없고 리뷰가 올 때 필요하다. **작업 지침으로 고정되어 있다**(`AGENTS.md`).

## Codex 리뷰가 도는 방식

저장소 소유자가 알려 준 동작이다(2026-09-30).

- **draft 를 풀면 Codex 가 스스로 리뷰를 시작한다.** 이때는 `@codex review` 를 남기지 않는다 — 겹친다.
  draft 동안에도 남기지 않는다. draft 에 Codex 봇이 「환경을 만들라」(create an environment)는 코멘트를
  남기는 것은 draft 라 리뷰하지 않는다는 뜻이다 — 설정 문제가 아니다
- **도는 중**이면 PR 본문에 👀 반응이 붙는다
- **끝나면** — 이상이 없으면 본문에 👍 반응을 남기고, 이상이 있으면 리뷰 코멘트를 남긴다
- **지적을 고쳐 커밋을 올린 뒤에는** `@codex review` 코멘트로 다시 요청한다. 답은 「문제 없다」는
  코멘트이거나 피드백 코멘트다

👍 반응과 「문제 없다」 코멘트는 그 라운드의 점수가 0 이라는 뜻이다(아래).

## 지적을 세는 법

PR 리뷰(Codex 등)의 지적을 **라운드마다 점수로 센다.** 점수는 분류를 요약할 뿐이고,
분류는 **실행으로** 가른다 — 같은 입력을 `main` 과 이 PR 에 넣어 보고, 저장소의 실제
파일에서 재현해 본다.

| 지적의 분류 | 점수 | 가르는 법 |
|---|---|---|
| 실결함 | 10 | 저장소의 실제 파일이나 CI 에서 재현된다 |
| 회귀 | 5 | 같은 입력에서 `main` 은 맞고 이 PR 은 틀린다 |
| 기존 한계 · 조용한 통과 | 2 | 저장소에 그런 입력이 없고 `main` 도 똑같이 놓친다 |
| 기존 한계 · 시끄러운 실패 | 1 | 저장소에 그런 입력이 없고 `main` 도 똑같이 실패시킨다 |
| 가상 입력 · 조용한 통과 | 2 | 검사 장치 · 스킬 사본(아래)이 받는 입력인데 저장소에 그런 입력이 없고, 검사가 그것을 조용히 통과시킨다 |
| 가상 입력 · 시끄러운 실패 | 1 | 같은데 검사가 그 입력을 거절한다(빨갛다) |
| 반박됨 | 0 | 재현을 시도했으나 지적한 현상이 어디서도 나오지 않는다 — 답글에 그 시도를 남긴다 |

한 지적은 **위에서부터 먼저 맞는 분류 하나**로만 센다 — 저장소의 실제 입력에서 틀리면
`main` 과 견줄 것 없이 실결함이다. **이 PR 이 새로 세운 경로에서 재현되면 실결함이다** — `main` 의 다른
경로가 같은 모양으로 틀려도(같은 검증기를 물려받았어도) 기존 한계로 내리지 않는다. 기존 한계는 `main` 에도
있는 **같은 경로**의 것이다(저장소 소유자가 정했다, 2026-10-02 — PR #71 1 라운드를 두 세션이 3 과 20 으로
갈라 셌다).

**검사 장치는 예외다**(저장소 소유자가 정했다, 2026-10-04 — PR #84). 판정 테스트 · 게이트처럼 **입력을 받아
판정하는 코드**는 리뷰어가 그 코드가 잘못 다룰 입력을 언제나 하나 더 지어낼 수 있다. 위의 「새 경로면
실결함」을 그대로 쓰면 저장소에 없는 입력까지 10 점이 되어 점수가 위험이 아니라 지어낸 입력의 수를 센다 —
PR #84 는 열 라운드 동안 0 에 닿지 않았다(`40 → 70 → 50 → 40 → 30 → 10 → 20 → 20 → 30 → 40`). 그래서 검사
장치에서는 **저장소의 실제 입력**에서 재현되는 것만 실결함 · 회귀이고, 그 밖은 가상 입력이다. 실제 입력은 그
검사가 **그 PR 의 head 에서 실제로 읽는 것**이다 — 저장소의 파일과, 그 파일을 짓는 코드가 지금 내는 출력. 코드를
고쳐야 나오는 모양은 가상 입력이다. 「짓는 코드가 낼 수 있는 모양」으로 넓히면 거의 모든 모양이 실제 입력이 되어
가르는 선이 사라진다(PR #86 Codex 리뷰 2 라운드). 가상 입력의 조용한 통과가 위험이 없다는 뜻은 아니다 — 그래서
아래처럼 이슈로 등록하고, 검사 장치를 보는 감사(`audit-quality`)가 그 자리를 다시 본다.

- 가상 입력은 **이 PR 에서 고치지 않는다.** 조용한 통과는 대장에 `audit-low` 이슈로 등록하고(방안 E),
  시끄러운 실패는 기록만 한다(방안 D). 답글에 그 분류와 이슈를 남긴다
- 검사 장치의 「알려진 한계」는 `AGENTS.md` 의 리뷰 지침에 적는다 — 리뷰어가 같은 부류를 거듭 내지 않게 한다
- **검사 장치는 리뷰 전에 입력을 닫는다.** 받는 입력의 모양을 실제 파일에서 전수로 뽑아 닫힌 목록으로 두고, 그
  밖은 거절한다 — 키워드만이 아니라 키워드의 조합과 값의 형까지. PR #84 는 이것을 리뷰가 짚을 때마다 한 칸씩
  해서 여덟 라운드를 썼다

**들여온 스킬의 사본도 가상 입력을 가른다**(저장소 소유자가 정했다, 2026-10-08 — PR #102). 머리 주석이
`pdw96/claude-kit@…` 에서 왔다고 적은 `.claude/skills/` 의 스킬은 claude-kit 원본의 사본인데, 이 레포는 그
스킬이 다루는 조각 문서를 쓰지 않는다. 그래서 이 레포가 겪지 않는 조각 상황 — 이 레포에 없는 PR 꼴, 네트워크가
막힌 닫는 PR 같은 것 — 을 짚은 사본의 지적은 가상 입력이다. 그런 상황에서 절차가 틀린 답을 내도 막는 것이
없으므로 조용한 통과로 센다. 이 규칙을 낳은 것은 PR #102 다 — 이런 지적을 사본에서 두 라운드 고쳤다. 그 PR 의
라운드는 이 규칙으로 다시 세지 않는다.

- 사본은 **이 레포에서 고치지 않는다.** 다른 레포에서도 같은 말이면 원본(claude-kit)으로 넘기고, 답글에 그
  분류와 넘긴 곳을 적는다. 답글에는 「원본으로 넘김」을 글자 그대로 쓴다 — 원본에 옮길 것을 그 말로 찾아 모은다.
  넘긴 지적에는 대장의 `audit-low` 이슈를 세우지 않는다 — 고칠 자리가 원본이므로, 아래에서 「이슈를 등록한 뒤」 ·
  「대장의 이슈로 등록돼 있다」고 하는 자리를 그 답글이 든다
- 사본을 고치는 것은 **이 레포만의 사정**일 때뿐이다 — 절차 지도 링크를 사본의 출처 커밋에 고정하는 것(PR #101 ·
  #102)이 그 예다

라운드 점수(그 리뷰의 합)로 다음을 정한다. **문턱은 가상 입력을 뺀 점수로 가른다** — 가상 입력은 이 PR 에서
고치지 않으므로 「고치고 계속한다」를 부를 수 없다(PR #86 Codex 리뷰). 가상 입력의 조용한 통과가 남은 라운드는
뺀 점수가 0 이어도 그 이슈를 등록한 뒤에 머지를 권한다. 추이를 보고할 때는 뺀 점수 옆에 가상 입력의 점수를
함께 적는다(예: `0 (가상 6)`).

- **5 이상** — 고치고 계속한다
- **1 ~ 4** — 고친다. **두 라운드 연속**이면 아래 방안을 검토한다
- **0** — 머지를 권한다. 머지는 저장소 소유자가 한다

**쏠림 신호.** 점수와 따로, 같은 **변경 단위**(함수 · 문서의 절 · 워크플로 스텝)를 짚은
지적이 두 라운드 연속 나오고, 두 라운드를 합쳐 그 단위의 지적이 세 건 이상이며 두
라운드 지적의 과반(절반 초과)이면 점수가 높아도 고치기를 멈추고 방안을 검토한다 — 고칠
때마다 새 틈이 나는 신호다. 라운드마다 한 건씩(합계 둘)이거나 단위마다 흩어져 있으면 이
신호가 아니다. ERP#18 은 2 라운드에 이 신호가 섰는데 3 라운드 뒤에야 방식을 바꿨다.

방안은 위에서부터 먼저 맞는 것을 쓴다.

| 방안 | 조건 | 소유자에게 묻는 것 |
|---|---|---|
| A. 진짜 구현으로 바꾼다 | 지적의 절반 이상이 한 규격을 손으로 흉내 낸 코드에 있고, 그 규격의 유지되는 구현이 있으며, 비용이 개발 의존성 하나 이하 · 운영 의존성 0 이다 | 의존성 추가 |
| B. 입력을 계약으로 좁힌다 | 검사 대상이 우리가 쓰는 몇 파일이고, 새 규칙에서 지금 걸리는 줄이 0 이거나 몇 줄이다 | 사람이 지킬 작성 규칙이 새로 생기면 |
| C. 기준 구현과 대조해 잰다 | 기준 구현이 있다. 무작위 입력 1만 개 이상에서 `main` 과 이 PR 의 판정을 **각각 기준 구현의 판정과 견준다** — `main` 이 맞고 이 PR 이 틀리면 「새로 틀림」, 반대면 「바로잡음」이다. **새로 틀림이 0.1% 미만**이고 바로잡음이 새로 틀림보다 많으면 받아들인다. 입력 생성기와 시드(또는 생성한 입력 묶음)를 PR 에 남겨 누구나 다시 돌릴 수 있게 한다 | 없음 — 결과를 보고한다 |
| D. 알려진 한계로 적는다 | 남은 것이 모두 기존 한계 · 시끄러운 실패다 | 없음 — `AGENTS.md` 에 적는다 |
| E. 후속으로 뗀다 | 지적이 이 PR 이 바꾼 변경 단위 밖이거나, 남은 것이 조용한 통과다 | 없음 — 조용한 통과는 D 로 덮지 않는다 |

신호가 섰는데 **어느 방안도 조건에 맞지 않거나**, 방안을 적용하고도 두 라운드 더 실결함 ·
회귀가 나오면 **혼자 더 고치지 않고** 분류표를 들고 소유자에게 묻는다(ERP#20 3 라운드가
앞의 경우였다).

**0 에 닿지 않고 닫는 길**(저장소 소유자가 정했다, 2026-10-04). 위처럼 물었을 때 소유자는 「남은 위험을
기록하고 머지」를 고를 수 있다. 조건은 둘이다 — 그 라운드의 지적이 **저장소의 실제 입력에서는 재현되지
않고**(남은 것이 모두 가상 입력이거나 기존 한계다), 남은 조용한 통과가 **머지 전에 대장의 이슈로 등록돼
있다.** 머지 전에 PR 본문에 그 결정과 점수 추이를 적는다. 이 길을 낳은 것은 PR #84 다 — 10 라운드에서
소유자가 닫았고, 남은 위험을 머지 **뒤에** 이슈 #85 로 등록했다. 이 규칙은 그 뒤에 섰으므로 PR #84 의 라운드를
이 규칙으로 다시 세지 않는다 — 그 PR 은 이 규칙의 사례가 아니라 계기다(PR #86 Codex 리뷰).

PR 을 보고할 때는 라운드 점수의 추이를 한 줄로 적는다(ERP#18 을 되짚어
매기면 `10 → 15 → 19 → 2 → 5 → 2 → 0`).

## 한 PR 은 한 세션이 몬다

저장소 소유자가 정했다(2026-10-02). PR #71 에서 두 세션이 같은 Codex 라운드를 따로 고쳐 같은 수정이 두 벌
났다 — 하나는 푸시 직전에 원격이 움직인 것을 보고 버렸다.

- **PR 을 연 세션이 몬다** — 리뷰 답글 · 고침 커밋 · `@codex review` 는 그 세션이 한다
- 다른 세션이 그 PR 에 커밋 · 답글을 달려면 **먼저 소유자에게 묻는다.** 넘겨받으면 연 세션에 그 사실을
  알리고(세션 사이 메시지), 연 세션은 그 PR 에서 손을 뗀다
- 넘겨받지 않은 세션이 할 수 있는 것은 읽기와 보고다 — 감사를 돌려 그 결과를 소유자에게 내는 것까지
