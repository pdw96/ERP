# ADR 0016 — 만료되지 않은 로트의 재검사는 트리거가 막는다

- 상태: 채택
- 날짜: 2026-10-02
- 정한 사람: 저장소 소유자(3단계 재검사 조각의 설계 게이트)

## 맥락

3단계의 재검사는 만료된 로트의 일이다 — 「만료되지 않은 로트는 재검사를 받지 않는다」
(`docs/schema-3단계.md` 「`inspections` 가 바뀌는 자리 — 재검사」). 그런데 「만료」는 재검사 줄
하나만 보고 가를 수 없다. 로트의 **지금** 만료일은 「가장 최근에 합격한 재검사의 갱신 만료일,
없으면 `lots.expiry_date`」이고, 그것을 판정 시각과 견줘야 한다 — **다른 표의 여러 줄**을 보는
조건이라 CHECK 로 적을 수 없다. 초안은 이것을 쓰기 경로와 트리거 가운데 어디서 막을지 「지으면서
정한다」로 미뤄 두었다.

`CLAUDE.md` 「금지」는 적어 두기만 하고 강제하지 않는 규칙을 막고, CHECK 로 적을 수 없는 규칙은
트리거가 건다고 적는다(ADR 0013).

## 대안

- **가) 트리거가 막고, 쓰기 경로가 먼저 이름으로 막는다.** `inspections` 에 재검사 줄이 들어올 때
  트리거가 가리키는 로트의 지금 만료일을 구해 판정 시각과 견준다. 쓰기 경로는 같은 조건을 먼저 물어
  업무 거절의 이름으로 돌려준다 — 조각 2 가 잔량에 쓴 모양이다(「트리거가 막는 것을 쓰기 경로가
  먼저 이름으로 막는다」)
- **나) 쓰기 경로만.** 단순하지만 지키는 것이 코드 한 곳이다. NC-70 이 낸 상태 — 「오늘 갈리지
  않는 것은 쓰는 코드가 하나뿐이라서이며 그것은 제약이 아니라 우연이다」 — 를 이 자리에 다시 만든다

## 결정

**가).**

- 트리거는 가리키는 로트 줄을 잠그고 지금 만료일을 구한다 — 같은 로트에 두 재검사가 동시에 오면
  둘 다 「아직 만료」를 보고 함께 서므로, 잔량 트리거(ADR 0013)처럼 로트 줄에서 줄을 세운다.
  잠금의 세기는 ADR 0013 이 겪은 교착(`KEY SHARE` 와의 충돌)을 보고 짓는 자리에서 정한다
- 견줌의 경계(만료일 당일이 만료인가)는 짓는 자리에서 정해 `docs/schema-3단계.md` 에 적는다 —
  트리거와 쓰기 경로가 **같은 경계**를 쓰는지 테스트가 본다
- 쓰기 경로의 거절 이름은 ADR 0014 의 열거에 더한다

### 트리거가 지킬 것 — 짓는 자리로 미루지 않는다

**원칙: 규칙이 읽는 것은 전부 고정하고, 고정할 수 없는 것은 같은 로트 잠금 아래에서 묻는다.**
「재검사를 받을 수 있는가」는 로트의 기준 만료일(`lots.expiry_date`) · 그 로트의 합격 재검사들 · 그
로트의 잔량을 읽는다. 셋 가운데 하나라도 규칙 밖에서 움직이면 — 고치든 지우든 — 이미 선 재검사가
소급해 틀리거나 서지 말아야 할 재검사가 선다. 그래서 **들어오는 순간 한 번 묻고, 그 뒤로는 읽은 것이
움직이지 않게 한다.**

PR #75 의 Codex 리뷰가 두 라운드에 걸쳐 여섯 자리를 하나씩 냈다(NULL 만료일 · 트리거 시점 · UPDATE ·
DELETE · 기준 만료일 · 실패 뒤 둘째 재검사). 같은 절에 지적이 몰리는 신호(`docs/리뷰-루프.md` 「쏠림
신호」)가 서서 저장소 소유자가 자리를 하나씩 막지 않고 원칙으로 적기로 정했다(2026-10-02). 아래는 그
원칙이 가르는 것이다 — 목록이 아니라 원칙이 기준이고, 짓는 자리에서 원칙에 걸리는 새 자리가 나오면
여기 더하지 않고 원칙대로 막는다.

- **읽는 줄은 고정한다.**
  - **재검사 줄은 UPDATE 도 DELETE 도 받지 않는다.** 지금 검사 줄은 반품이 가리킬 때만, 그것도
    UPDATE 만 막힌다(`inspection_stays_behind_its_returns`). 재검사 줄의 로트 · 판정 시각을 고치면 만료
    되지 않은 로트로 옮겨 가고, 합격 재검사를 지우면 지금 만료일이 기준 만료일로 되돌아가 갱신된 로트가
    다시 재검사를 받는다. 판정 기록을 고칠 정당한 경로가 아직 없다 — 오기를 고치는 길은 그 길이 서는
    조각에서 새 사실로 연다(원칙 ⑦)
  - **`lots.expiry_date` 는 고치지 않는다.** 지금은 `lots.quantity` 만 고정된다(`lot_quantity_stays_with_its_ledger`).
    기준 만료일을 잠깐 과거로 돌려 재검사를 넣고 되돌리거나, 앞으로 밀어 이미 선 재검사를 소급해
    무효로 만들 수 있다. 라벨에 찍혀 나간 값이라 고칠 까닭도 없다(`PRD.md` 성공 기준 5)
- **고정할 수 없는 것은 같은 잠금 아래에서 묻는다.**
  - **잔량이 0 보다 커야 한다.** 원장은 움직이는 것이 정상이라 고정할 수 없다. 로트 잠금은 같은 로트의
    두 재검사를 줄 세우지만, 앞의 것이 불합격해 잔량 전부를 폐기출고로 내면 뒤의 것은 여전히 「만료」를
    보고 선다 — 없는 물건을 검사한 기록이 된다. 「재검사를 기다리는 로트」의 정의(`docs/schema-3단계.md`)가
    이미 잔량을 요구하므로, 트리거는 로트 줄을 잠근 **뒤에** 만료와 잔량을 함께 묻는다
- **묻는 식 자체의 두 자리.**
  - **지금 만료일이 없으면(NULL) 만료가 아니다 — 거절한다.** 무기한 로트(`shelf_life_days` NULL)는
    `expiry_date` 가 NULL 이고, SQL 의 NULL 견줌은 막지 못한다. NULL 분기를 따로 둔다
  - **지금 만료일은 들어오는 줄을 빼고 구한다 — `BEFORE INSERT` 다.** `AFTER INSERT` 면 방금 넣은
    합격 재검사의 갱신 만료일이 「가장 최근」으로 잡혀 정상 재검사가 전부 거절된다

**테스트가 무는 것** — 위의 자리마다 트리거 쪽 하나(쓰기 경로를 거치지 않고 SQL 로), 쓰기 경로 쪽 하나.
동시성은 두 연결로 잰다 — 앞의 것이 합격인 경우와 불합격인 경우를 따로. 고정은 UPDATE · DELETE 를
SQL 로 직접 보내 거부되는 것을 본다.

## 결과

- 재검사를 내는 길이 몇 개가 되든 「만료 로트만」 규칙은 한 자리에 산다
- **모델에 보이지 않는 규칙이 하나 더 는다.** ADR 0013 의 결과와 같다 — 트리거의 정의를 따로
  견주고, 트리거를 지우거나 조건을 뒤집으면 빨갛게 되는 것을 본다(`docs/audit/mutations.md`)
- 같은 조건이 트리거와 쓰기 경로 두 자리에 적힌다. 「목록을 두 벌 두지 않는다」의 예외가 아니다 —
  강제하는 것은 트리거 한 자리이고 쓰기 경로는 이름을 주려고 먼저 묻는 것이며, 둘이 갈리면 트리거가
  이긴다(이름 없는 거절이 난다). 갈리는 것은 위의 경계 테스트가 문다
- 트리거가 못 보는 부류는 ADR 0013 과 같다 — 트리거를 끄고 넣는 길은 권한의 일이다
